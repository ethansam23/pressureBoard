# Downhole Link Protocol — Wire Specification & External Requirements

_The one-way digital UART stream from the pressure transmitter to the
battery/logger. Firmware source of truth: `app/link_frame.h` (code map,
timing constants) and `app/link_tx.c` (transmit engine). This document also
carries the **open questions for the logger designer** — several assumptions
below are GATES, marked as such, and must be confirmed before deployment._

---

## 1. Physical layer

| Item | Value |
|---|---|
| UART | 9600 baud, 8N1 (byte = 1041.7 µs, bit = 104.17 µs) |
| Pin | **P1.0** (UART2 TXD), push-pull ~5 V logic when driven |
| Direction | One-way: transmitter → logger. Nothing ever drives the line toward the transmitter |
| Idle state | High (UART idle) |
| **Reset behavior** | **P1.0 is HIGH-Z while the MCU is in reset** — the transmitter cannot hold the line idle-high through its own reset/brownout. **An external pull-up on the harness/logger side is required** so resets present as clean idle, not floating noise. **GATE Q16/Q17** |
| Transmitter baud accuracy | +0.005 % (40 MHz crystal-derived, fractional divider) — far inside the receiver's stated ±2 % window |

## 2. Packet format

```
|0x7F| >2 ms gap |MSB|LSB|CHK|   ...>20 ms idle...   repeat
```

- **Sync byte `0x7F`** — the receiver's auto-baud reference (its RC oscillator
  drifts with temperature).
- **Gap** — sync stop-bit end → first data start bit: the firmware produces
  **2.90–4.9 ms** (spec: >2 ms).
- **Data block** — exactly three bytes, back-to-back (ISR-chained, no
  software-induced inter-byte gaps): `MSB`, `LSB`, `CHK`.
- **Checksum** — `CHK = ~(MSB + LSB) & 0xFF`. This is an **additive checksum,
  not a CRC**. Known limitations (accepted; protocol is logger-defined):
  swapping MSB/LSB preserves the sum; compensating byte errors pass; random
  corruption is accepted ~1/256. The defense is continuous retransmission —
  any single bad packet is displaced 110 ms later.
- **Total packet** (sync start bit → checksum stop-bit end): firmware
  guarantees **≤ 9.17 ms** (spec: <10 ms; test limit 9.3 ms; scope limit 9.5 ms).
- **Idle** — checksum end → next sync: **≥ 22 ms enforced**, **~100.8 ms
  nominal** (spec: >20 ms). The enforced floor still guards the logger's
  20 ms line and is unchanged; the nominal gap is set by the period.
- **Period** — sync-start → sync-start, **110 ms nominal (~9.1 packets/s)**,
  rebased on each actual sync start. Overdue packets (after an NVM save or a
  fenced stall) fire once at the first legal opportunity — **never a
  catch-up burst**.

**PAYLOAD IS SACRED:** `MSB`, `LSB`, and `CHK` may each legally equal `0x7F`.
There is no byte-stuffing, no escaping, and measurement values are never
altered to avoid byte patterns. Framing is assumed **gap-based** per the
timing diagram: once the receiver accepts a sync byte after the long idle, it
reads exactly three positional bytes without re-synchronizing. **GATE Q3–Q6.**

## 3. Payload encoding (16-bit, big-endian: MSB first)

| Code | Meaning |
|---|---|
| `0` – `10000` | Pressure, **0.1 bar/LSB**, absolute scale 0 – 1000.0 bar |
| `0xFF01` | `NO_READING` — boot, before the first sample (stream is alive within ms of power-on) |
| `0xFF02` | `UNCAL` — no valid calibration (also: non-finite internal computation). Never raw counts disguised as pressure |
| `0xFF03` | `DISAGREE` — the two probes disagree beyond threshold |
| `0xFF04` | `ADC_STALL` — ADC conversions dead |
| `0xFF05` | `VDDEXT` — sensor excitation rail unstable |
| `0xFF06` | `OVER_RANGE` — computed pressure > 1010.0 bar |
| `0xFF07` | `UNDER_RANGE` — computed pressure < −5.0 bar |
| `10001`–`0xFEFF`, other `0xFFxx` | Reserved / never transmitted |

Fault priority (one code per packet; highest wins):
`ADC_STALL > VDDEXT > DISAGREE > UNCAL > range codes > pressure`.

Encoding policy (float domain, before integer conversion): non-finite →
`UNCAL`; < −5.0 → `UNDER_RANGE`; −5.0…0 → `0`; round-half-up to deci-bar;
1000.0–1010.0 → `10000` (explicit tolerance clamp: 1009.9 bar logs as
1000.0); > 1010.0 → `OVER_RANGE`.

**The 16-bit field is permanently pressure/status.** There is no room to ever
report temperature or a second quantity without renegotiating this protocol
(the planned temperature-compensation LUT is applied on-board, invisible
here). **Q20.**

## 4. Rate & availability metrics

| Metric | Value |
|---|---|
| Nominal packet rate | ~9.1 /s (110 ms period) — was 25 /s (40 ms) through step 4b |
| Max interval between valid packet starts | ≈ **145 ms** (one fenced stalled-ADC refresh, ≈once/second while the ADC is faulted) · ≈ **135 ms** around an NVM save (bench-command-triggered only) |
| Sustained rate during an ADC fault | ≈ 8.7 valid packets/s — all packets complete; the design produces **no partial packets** for any predictable stall |
| Supported logger record rate (2× rule) | ≤ **4.5 Hz** nominal, ≈ 4 Hz under worst-case fault conditions — **down from 12.5 / 11 Hz** at the old 40 ms period. **GATE Q7 (now load-bearing):** the 110 ms period was adopted on the tool owner's call with Q7 still open. If the logger records above ~4.5 Hz the 2× rule is violated and the period must go back down. Confirm the logger's actual rate AND whether "2×" applies to average rate or maximum gap |
| Bench exception | While a debug-build console session is open (`CONSOLE UNLOCK`), the stream is **suspended entirely** — the line carries text instead. Mutual exclusion: packets and text never interleave |

## 5. Dead-transmitter detection — the logger's staleness rule (DEPLOYMENT BLOCKER)

The old analog output was fail-safe by physics: a dead board decayed the line
to 0 V, visibly out-of-band. Digitally, a dead board (hard fault, watchdog
Sleep-Mode latch, cut line, MCU reset) is **silence** — and a logger that
"uses the latest received data" would re-record the last value forever,
making a tool that died at hour 2 indistinguishable from 70 flat hours.

**Required:** if no checksum-valid packet arrives within a timeout, the
logger must record a distinct "no data" marker (not the stale value).
Recommended timeout: **500 ms** (≈4.5 nominal packet slots; > the 145 ms worst
legitimate gap by ~3.4×). The margin was 12 slots / 6× at the 40 ms period —
still workable, but a logger that debounces over a couple of slots now has far
less room. **GATE Q1/Q11/Q18/Q19.**

## 6. Timing measurement note (TI hypothesis)

Firmware timestamps bytes at the UART TI interrupt. **Working hypothesis
(stated in no local hardware document; 8051-heritage inference): TI may
assert at the stop-bit START, one bit-time before the frame physically
completes.** All firmware idle arithmetic adds a conservative one-tick
allowance on top of TI timestamps; nothing is named "wire done". The exact
TI-to-stop-bit offset is a **hardware verification gate** (scope measurement,
see `verification_guide.md`).

## 7. Questionnaire for the logger designer

Conformance gates (protocol behavior):
1. Does `>20 ms idle` mean absolutely no UART activity from checksum
   completion until the next sync?
2. Can arbitrary console bytes legally appear between packets? *(Firmware no
   longer emits any — mutual exclusion — but the answer defines wire law.)*
3. Must the sync byte be the first line activity following the long idle?
4. Does the receiver only accept `0x7F` after detecting the timing gap?
5. Once sync is accepted, does it read exactly three bytes regardless of
   their values?
6. May data byte 1, data byte 2, or the checksum equal `0x7F`?
7. What is the maximum logger recording frequency — and does the ≥2×
   requirement apply to average packet rate or maximum packet gap?
8. Does the receiver auto-baud on every packet (RC drift over temperature)?
9. How does it recover from sync-only, truncated, or checksum-invalid
   packets?
10. Are fault/status codes (≥ `0xFF00`) excluded from any averaging?
11. What staleness timeout is implemented (we recommend 500 ms)?
12. Is the `<10 ms` packet limit measured from the sync start bit to the
    checksum stop bit?
13. Is the sync gap measured from the end of the sync stop bit to the start
    of the first data start bit?
14. Is byte order definitely MSB first, then LSB?
15. Is the checksum exactly the 8-bit inverse of the modulo-256 byte sum?

Deployment gates (system integration):
16. What voltage and idle-state behavior does the logger expect at its input
    divider?
17. Who holds the data line idle-high while the transmitter is in reset?
    (Our pin is high-Z then — an external pull-up is required.)
18. What is recorded when packets become stale?
19. Is a partial packet tolerated (sync + silence after an abort), or must
    packets complete atomically? *(Firmware: atomic for all predictable
    stalls; a sync-only fragment is possible only after an unpredicted stall,
    followed by ≥22 ms quiet and a clean packet.)*
20. Can the protocol ever be extended to report temperature, or is the
    16-bit field permanently pressure/status only? *(We assume permanent.)*

Answers should be recorded here, dated, before deployment sign-off.

## 8. Logger-side data handling (wording agreed with user)

The logger performs **no calibration, compensation, unit conversion, or
nonlinear processing**. It may select the latest valid pressure code or
average **valid pressure codes only** — status codes (≥ `0xFF00`) are stored
verbatim and must be excluded from pressure averaging (averaging `0xFF03`
with pressures produces garbage). Transition windows (pressure↔fault) and
stale data need defined behavior on the logger side — **Q10/Q17–Q19**.
